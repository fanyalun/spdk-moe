# 可逆编码原理与 Nsight 实测

## 编码单元与例子

每个 Gate、Up、Down 矩阵先按现有 64 列布局打包，再分成最多 1 MiB 的块。
每块独立选择缩放指数 `s`、整数基值 `base` 和位宽 `bits`，不按行编码，
也不把多个专家一起编码。56 MiB 的矩阵有 56 个编码块，一个专家有 168 个。

假设块中有三个 FP32 值：

| 步骤 | 值 |
| --- | --- |
| 原值 | −0.375，0.125，0.5 |
| 精确乘以 8 | −3，1，4 |
| 减去基值 −3 | 0，4，7 |
| 每值所需位宽 | 3 位 |

编码元数据为 `s=3, base=-3, bits=3`，三个差值占 9 位，载荷按字节存为
`e0 01`。解码先校验载荷，再取出差值 `delta`，恢复：

```text
x = float(base + delta) × 2^(-s)
```

此例已调用实际编码器验证，恢复结果与原始 FP32 字节一致。三个值只是
说明算法，24 字节块元数据对这种小样本并不经济；实际块通常有 262144 个值。
编码器逐值验证 FP32 位模式，无法满足精确恢复的块保存原始字节。

本次实际盘上第一个块为 `s=24, base=-16777189, bits=25`，元素 262144 个。
载荷从 1048576 字节变为 819200 字节。25 位 AVX2 路径每次解包 8 个差值，
加回基值，转为 FP32，再乘二进制缩放因子；26–31 位使用标量路径。

基值大不必然导致载荷大。例如 `[1000000, 1000001, 1000003]` 可以保存
`base=1000000` 和差值 `[0,1,3]`，每值只需 2 位。当前实现要求缩放整数
适合 int32，超出范围或差值需要 32 位时回退原始格式，尚未实现更宽基值。

整数与小数分离也是可逆方案，但需要分别记录和解码两个数据流，保持符号、
负零及精确 FP32 恢复。这可能有利于整数部分高度重复且小数部分可压缩的块，
也可能增加元数据和解码成本；当前未实现或测试这种拆分。

## 2026-10-13 实际 profile

使用 Nsight Systems 2025.1.1，NVTX 和 OS runtime tracing，禁用容器不支持的
CPU sampling/context-switch 采集。条件与此前本地实验一致：Gold 6248、
NVMe 文件上的 AIO O_DIRECT、八槽位、FIFO、1 MiB、I/O 深度 4、计算线程 1。
owner 在 CPU 10，计算线程 CPU 1，发起器 CPU 0。
16 次预热 seed 777，50 次计时 seed 42，另外一个 seed 4242 输入校验误差为 0。
计时输入摘要与前六轮相同，CPU throttling 增量为 0。

`WEIGHT_IO` 在提交成功时开始，在完成回调入口结束，先结束 I/O 再开始
`DECODE`，避免把解码自身计为该次 I/O。解码标记包括校验与 FP32 写回。
分析逐请求核对 NVTX 读取和解码字节与 store 诊断计数一致。

50 次计时请求的平均结果：

| 项目 | 毫秒 |
| --- | ---: |
| target 请求 | 365.483 |
| TCP 往返 | 366.025 |
| 专家计算区间 | 152.212 |
| 解码区间 | 282.570 |
| 解码与计算重叠 | 116.030 |
| 解码与计算区间并集 | 318.752 |
| 存在未完成 I/O 的区间 | 358.648 |
| 并集与未完成 I/O 重叠 | 312.547 |
| 并集落在 I/O 之外 | 6.205 |
| Route / Top-K | 0.357 |
| 聚合 | 0.068 |

计算的 96.054%、解码的 99.930%、两者区间并集的 98.053%，与未完成 I/O
重叠。平均 miss 为 7.86，解码每个 miss 专家约 35.950 ms，约每矩阵
11.983 ms。实际流式恢复吞吐约 4.900 GB/s，明显低于先前暖缓冲测试的
9.43 GB/s。完整 capture 的 88536 个解码块平均约 0.214 ms，P99 约
0.303 ms；该块统计包含预热与准确性请求。

profile 下的 TCP P99 为 477.767 ms，是 50 样本中的最大值。
该请求解码 285.772 ms、计算 152.377 ms，与中位附近请求的解码 285.535 ms、
计算 152.992 ms 相近；主要差异是 I/O 区间以及 I/O 存在而两者均未执行的
区间，后者从约 44.834 ms 增加到 143.350 ms。这只能定位到等待/完成处理
路径，不能进一步归因为 SSD 硬件、内核、调度或队列。profile 数值不是
无插桩的正式性能成绩。

## 能否被 I/O 覆盖

当前本机的时间重叠充分，但不能将 282.570 + 152.212 当作串行耗时；
两者在不同线程上，需减去共同执行时间。矩阵必须完整解码才能开始其计算，
最后一个 Down 计算及聚合仍有尾部依赖。

“未完成 I/O”也不等同于 SSD 一直传输数据。同步解码占用 owner 线程，
会推迟新 I/O 的提交和其他完成回调，从而延长软件观测到的 I/O 区间。
owner 解码已占平均请求时间约 77.3%，平均未完成 I/O 数约 2.96。
因此 98% 时间重叠不能证明解码无成本或系统仍完全受 SSD 限制。

按照官方标称 7 GB/s，八专家全 miss 的编码读取量约 1.101 GB，理想读取
时间约 157.3 ms。如果解码仍保持本机观测到的 4.90 GB/s，恢复完整
1.409 GB FP32 需约 287.6 ms，已经超过这个理想 I/O 窗口。要消费满
7 GB/s 的编码输入，FP32 恢复吞吐约需 `7 / 0.78125 = 8.96 GB/s`。
这只是条件模型，官方 CPU 与本机不同，必须实测。

后续应针对 owner 解码占用研究独立解码线程、I/O 提交与解码调度，以及
真正流式条件下的 SIMD/校验/内存写回优化；需要同时测 P99 和总内存，
不能仅依据暖缓冲解码速度或重叠比例选择方案。
