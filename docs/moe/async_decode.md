# 独立解码线程

生产入口保持整矩阵流水线，使用I/O深度16、1个计算线程和8个专家槽位。已测1/2解码线程速度接近，暂选1线程为默认；8线程追加结果见文末。RPC增加 `decode_threads`，范围0至8；省略时为0，保留同步回调解码兼容路径。独立解码仅用于lattice编码。

reactor在读取回调中释放I/O并将编码块交给解码队列，随后可继续提交读取。解码线程执行原有校验和无损解码，写入各自块对应的专家缓存区域，再通过SPDK消息通知owner；只有owner更新完成计数、就绪前缀和矩阵完成状态。计算仍等待整矩阵解码完成。

I/O在途及资源等待最多为 `io_depth`，异步路径总共预分配 `2 × io_depth` 个编码缓冲槽位，覆盖读取、待解码、解码中和等待owner确认的块。缓冲区在owner处理解码完成前不会复用；池耗尽时停止新增读取，队列不会扩容。深度16时为32个 `1MiB+4KiB` DMA缓冲区，来自既有256MiB池，不增加专家缓存或扩大SPDK池。

解码线程与计算线程均绑定在reactor所在NUMA节点的不同物理核心上，避开reactor及彼此的SMT同胞。线程在启动预热前创建，关闭时先等待读/解码全部完成，再停止并join线程、释放内存。取消或解码失败仍保留所有未完成块的引用，直到其完成通知被owner消费。

```json
{"method":"bdev_moe_create","params":{"name":"moe_bdev_0","backend":"nvme","base_bdev":"ScoringNvmen1","weight_dir":"/tmp/moe_weights","pipeline":"matrix_fifo","weight_encoding":"lattice","cache_slots":8,"io_depth":16,"io_size":1048576,"decode_threads":2,"compute_threads":1}}
```

构建仍使用现有SPDK流程，不增加依赖。小规模验证可复用pipeline测试：

```sh
make -C module/bdev/moe -j2
make -C examples/moe/tgt -j2
make -C test/moe/tile_progress -j2
MOE_TEST_WIDE=1 MOE_TEST_FIFO=1 MOE_TEST_ENCODING=lattice \
  MOE_TEST_LATTICE_WEIGHTS=1 MOE_TEST_CASE= MOE_TEST_IO_DEPTH=16 \
  MOE_TEST_DECODE_THREADS=2 MOE_TEST_STARTUP_WARMUP=16 \
  python3 test/moe/test_moe_pipeline.py
```

测试需要reactor、计算、解码各自可用的不同物理核心。诊断日志增加 `decode_threads`、`decode_peak`、`decode_pending` 和 `codec_buffer_slots`。`decode_peak`包含排队、执行及等待owner确认的块；解码累计ticks在并发模式下是各工作线程耗时之和，不能直接解释为端到端解码窗口。

原生NVMe性能验证固定matrix_fifo、深度16、AVX2、1计算线程、8槽位和相同权重，比较decode_threads=0/1/2。同构建0线程为匹配对照。每组独立精度校验50次、内部预热16次，每轮外部预热16次，计时50次，测2轮取较低P99；监测目标RSS高水位、去重HugeTLB及实际入口进程峰值，不额外施加cgroup限制。

独立构建已通过，目标二进制SHA256为 `a414c836fb71f604af5b54f170349bad42fc2e139a5c020b396cd35f25d14874`。启动器5项测试和I/O资源等待/取消回归均通过。D=128、H=4096、9专家、Top-8的小规模测试中，深度16、双解码线程的冷启动与预热16次两组各32个正常请求最大绝对误差均为0，每个请求结束后decode_pending为0。默认深度4的损坏Down矩阵用例通过拒绝及恢复后32次准确推理，执行中关闭用例通过资源排空检查。

故障用例最初因测试脚本不允许对非正常用例覆盖深度而在启动前被拒绝；改用默认深度4后通过，未因此修改候选源码。格式门禁仍返回1，日志与此前既有格式问题完全一致，未修改无关文件。

## 原生NVMe结果

每组均完成上述50次独立精度校验与两轮各50次计时，误差均为0，输入摘要一致，目标正常退出。内存上界包含目标RSS历史高水位、去重HugeTLB和实际启动器RSS历史高水位，不包含外部initiator。

| 配置 | 第一轮P99 | 第二轮P99 | 较低P99 | 保守进程内存上界 |
|---|---:|---:|---:|---:|
| 原V3、深度16，追加复测 | 397.650272ms | 399.561187ms | 397.650272ms | 1,713,393,664 bytes |
| 新构建同步回调解码 | 407.459138ms | 407.632298ms | 407.459138ms | 1,713,315,840 bytes |
| 1个独立解码线程 | 386.115568ms | 387.136125ms | 386.115568ms | 1,713,238,016 bytes |
| 2个独立解码线程 | 387.345313ms | 388.037146ms | 387.345313ms | 1,713,336,320 bytes |

四组上界再加64MiB筛选余量仍低于十进制2GB。相对追加的原V3复测，单解码约降低2.90%，双解码约降低2.59%；两者相差约0.32%，不能认定稳定速度差异，选择单线程主要为了少占一个核心。同步兼容路径为何慢于原V3尚未定位，不能把相对该路径的5.24%全部称为原V3加速收益。

计时阶段100ms采样的CPU峰值，两种异步路径均约240%，同步对照约160%，其中100%表示一个逻辑核心。双解码两线程确实各分担约153ms CPU时间，但没有进一步降低P99；目前没有证据继续增加解码线程能改善本配置的关键路径。成绩仅适用于本机和本组权重/输入，不代表官方机器成绩。

上一阶段选择默认1线程只改变Python入口参数，C二进制与正式测得decode_threads=1时相同；历史运行manifest保留当时默认2及显式覆盖配置，入口另做dry-run和启动器验证。

## 8线程追加验证与停止状态

解码线程上限从4扩大至8，隔离构建二进制SHA256为 `370805af915022b664c7b4f97865401d6959494d95beb2424c2d614a3192f27f`。小规模冷启动与预热两组各32次推理误差均为0，8个解码线程分别绑定独立物理核心，请求结束后decode_pending为0。

原生NVMe的8线程组已完成50次独立精度校验，误差为0；两轮各50次的P99分别为386.305994ms和386.147818ms，取较低值386.147818ms。目标进程CPU的100ms采样峰值约239.67%，内存保守上界1,713,778,688 bytes，加64MiB余量仍低于十进制2GB。8解码、1计算和1个SPDK reactor共占10个不同物理核心；深度16表示最多16个未完成请求，不是16个I/O线程。

用户随后要求停止实验。控制器、目标及监测进程已退出；同一新构建的1线程对照在导入阶段被中止，没有成绩。此前1线程成绩来自上一构建，只能作历史参考，不能声称完成了新构建的配对比较；当前未观察到8线程相对历史成绩的明显改善，默认仍沿用1线程。

构建后的外部记录脚本曾误用 `build/bin/moe_tgt` 路径，记录哈希时报FileNotFoundError，先报告后仅更正为 `build/examples/moe_tgt`。主动停止对照时，设备注销使等待中的创建RPC返回No such device；此为人工中止记录，未修改候选源码，也不作为自然运行失败计分。
